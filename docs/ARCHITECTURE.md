# Architecture

This document describes how `db-collation` reproduces a database's collation
locally. It is intentionally small: one crate, a closed set of backends, and a
pure comparison function.

## Overview

```
               caller
                    │  resolves source metadata (provider, locale, version, ...)
                    ▼
        Collation (resolved description)
                    │
        ┌───────────┼────────────────────┐
        ▼           ▼                    ▼
    Binary      PostgresIcu          MysqlUca
  (bytes)   (ICU4C, per-thread)   (UCA weight tables)
        └───────────┼────────────────────┘
                    ▼
             compare(&str, &str) -> Result<Ordering>
```

A `Collation` is a **resolved description**, not a name. The caller discovers
what the source actually uses — provider, locale, determinism, version — and
constructs the description. The library never performs discovery and never talks
to a database.

## The comparison contract

A `Collation` is a total preorder over strings. It guarantees:

1. **Reflexivity / transitivity** — as required by any sort or binary search.
2. **Exactness** for supported configurations — identical to the source
   database's operator.
3. **Fail-closed construction** — an unsupported description is rejected before
   it can produce a wrong comparison.

`compare` is the primitive. Sort keys are deliberately *not* part of the stable
API: a deterministic collation's order includes a value-level bytewise tie-break,
which is not captured by a single opaque byte-string key, so exposing one would
invite incorrect use.

## Backends

### Binary

Bytewise lexicographic ordering over the UTF-8 encoding, with shorter-first on a
prefix. This is exactly PostgreSQL `C`/`POSIX` and MySQL's `utf8mb4_0900_bin`
(NO PAD, code-point order). Always available, no dependencies. The legacy
`utf8mb4_bin` (PAD SPACE) is *not* bytewise and is refused.

### PostgreSQL ICU

Mirrors `varstr_cmp` in `src/backend/utils/adt/varlena.c` (REL_16_STABLE):

1. Call `ucol_strcollUTF8` on the database-encoding bytes.
2. If the result is equal **and** the collation is deterministic, break the tie
   with a bytewise comparison, shorter string first.

Nondeterministic collations omit step 2, so ICU equality is SQL equality.

ICU4C collator handles (`UCollator`) are `!Send + !Sync`. We do not store a
handle in the `Collation`; instead we open one per thread, keyed by locale, in a
thread-local cache. This keeps `Collation: Send + Sync` and avoids repeated open
cost. See `src/thread_local.rs`.

### MySQL UCA

MySQL's `utf8mb4` UCA collations assign each code point one or more 16-bit
weights and compare the concatenation. Our tables (UCA 4.0.0 for
`utf8mb4_unicode_ci`, UCA 9.0.0 for `utf8mb4_0900_ai_ci`) are generated from the
Unicode UCA `allkeys` data and follow MySQL's semantics:

- **Primary-only, folded.** Each collation element's primary weight is kept,
  zero primaries dropped (that is MySQL's accent/case-insensitive level).
- **NO PAD** (`utf8mb4_0900_*`): compare concatenated weights directly.
- **PAD SPACE** (`utf8mb4_unicode_ci`): drop zero weights, then pad the weight
  sequence with the space weight (`0x0209`) to the longer length.
- **Default-ignorable code points** get zero weight rather than an implicit
  weight (MySQL excludes `Default_Ignorable_Code_Point` from implicit-weight
  construction).
- **Multi-element weights are emitted in MySQL's order** — first element first,
  matching `WEIGHT_STRING('½') = 1C3E06261C3F` ⇒ `[1C3E, 0626, 1C3F]`.
- **Out-of-table implicit ranges** (Tangut, CJK extensions, Hangul jamo
  decomposition) reproduce MySQL's `next_implicit`, derived entirely from
  `allkeys`: code points absent from the file take MySQL's implicit weight.
  Default-ignorable code points are listed with zero primaries in `allkeys` and
  are therefore *not* special-cased. UCA 4.0.0 uses its own narrower range rules
  and a whole-character `[0xFBC1, cp]` fallback for over-long expansions.
- **Streaming, allocation-free.** Comparison walks both strings character by
  character, emitting each character's weight elements into a fixed stack buffer
  (`WeightBuf`, eight elements) and comparing elements as they are produced, so
  it short-circuits on the first difference and never allocates for the string
  contents. Under PAD SPACE the exhausted side is padded with the space weight.

Every rule was established against live MySQL with the differential harness and
the full-BMP sweep, using the real crate as the candidate.

Weight tables live in `src/mysql/table_*.rs` and are regenerated by
`harness/gen_weights.py` from the vendored `allkeys` files in `harness/data/`.

### Oracle UCA

Oracle's `UCA*_DUCET` collations are the Unicode Collation Algorithm (UTS #10)
over the **open** Unicode DUCET tables, with Oracle's default parameters
`_S4_VS_BN_NY_EN_FN_HN_DN_MN`. Unlike the MySQL backend this is a full
quaternary/shifted UCA, so the backend keeps each collation element's primary,
secondary, tertiary and variable flag. `src/oracle/uca.rs` implements:

- **Fixed-version NFD** — canonical decomposition (with algorithmic Hangul
  decomposition) and canonical ordering by combining class. Decomposition and
  combining-class data are pinned to a **single fixed Unicode version (15.0)**
  for *both* named collations: probing the live source shows it reorders
  combining marks added through Unicode 15.0 (e.g. U+0898, U+10EFD) under both
  `UCA1210_DUCET` and `UCA0700_DUCET`, while code points added later (e.g.
  U+105C9, U+10D69 in 16.0) stay atomic. Normalization therefore does **not**
  follow the UCA weight-table version. This is deliberately *not* a
  general-purpose normalizer.
- **Contiguous and discontiguous contractions** (UTS #10 §7.2): the longest
  contiguous table match is then extended across following **unblocked
  non-starters**, so a contraction such as `и` + breve is still found with a
  lower-class mark (U+0591) between the two. A starter, or a mark whose
  combining class is `≥` the mark being matched, blocks the extension and the
  skipped mark is processed on its own. A mark that *extends* a match is removed
  from the stream, so the remaining marks become logically adjacent and a
  consumed mark can never take part in a second contraction. Then single code
  points, then synthesised **implicit weights** for code points absent from the
  DUCET (UTS #10 §10.1.3), including Oracle's fixed Tangut/Nushu ranges and the
  Han core/extension `FB40`/`FB80` leads — including CJK Extensions G/H
  (U+30000..U+3134A, U+31350..U+323AF), which the live source applies to both
  named versions even though they postdate the UCA 7.0 data.
- **Shifted variable weighting** — variable elements move to the quaternary
  level, non-variables take `FFFF`, and ignorables following a variable are
  suppressed at every level (UTS #10 §4).
- **Level-by-level comparison** L1 → L2 → L3 → L4 and stop; Oracle has no
  `identical` level, so strings equal at L4 compare equal.

Oracle caps its UCA sort key at 2000 bytes; past that it truncates, so the
backend refuses any input whose collation-element count could reach the cap
(a conservative over-approximation — refusing is safe, returning a wrong order
is not). This is surfaced as [`Error::InputLimit`]: a per-input fall back on an
otherwise supported configuration, distinct from a construction refusal.

Weight tables live in `src/oracle/table_*.rs` and are regenerated by
`harness/gen_uca.py` from the vendored `allkeys` and `UnicodeData` files in
`harness/data/`.

## Input domain

`compare`/`equal` operate on `&str`, so inputs are always valid UTF-8. The model
reproduces the ordering of:

- `PostgreSQL` `text`/`varchar` (and `name`) under the described collation;
- `MySQL` `utf8mb4` string values;
- `Oracle` `VARCHAR2` values on an `AL32UTF8` database.

It does **not** model:

- `PostgreSQL` `bpchar`/`char(n)` — trailing-space-padded comparison differs from
  `text` even under the same collation;
- `Oracle` `CHAR`/`NCHAR` (blank-padded) and non-`AL32UTF8` charsets — refused at
  construction;
- `citext` (extension type) — its case-insensitive comparison is a type-level
  transform applied before the collation, not the collation itself;
- non-UTF-8 source encodings, or values that must first be transcoded;
- embedded NUL handling beyond what the collator sees (a `&str` may contain NUL;
  whether the source stores/compares it the same way is the caller's concern).

## What is intentionally out of scope

- Any network or database access.
- Discovering source metadata.
- Approximating a collation that is not modelled.
- Non-UTF-8 encodings and ill-formed UTF-8 (rejected as `&str` cannot hold them).
